# Performance measurements

Results for the budgets. `cargo xtask budgets [--ci]` builds `kiln-bench` in release mode,
measures every budget of `bench/budgets.toml` that has a benchmark, and rewrites the generated block below
(between the `kiln-bench` markers; do not edit it by hand). CI runs it on every push and uploads this file as
the `perf-<run>` artefact. Measurements taken outside `kiln-bench` (build times) are recorded by hand in the
sections after the block, each with its date, machine and command. Budget exceptions approved at a gate are
listed under "Exceptions".

Machine: the development machine (Ubuntu 24.04.5, 4 CPUs, 7.5 GB RAM), Rust 1.99.1,
`.cargo/config.toml` as committed (3 jobs, sccache, dependencies at `opt-level = 2`).

## B5 — typing latency in the 300-page document (budget p95 ≤ 33 ms keystroke → screen; interim < 60 ms)

Measured by `e2e/specs/write.spec.ts` ("B5: keystroke to paint on the 300-page document") on a
production build (`vite build` with `VITE_KILN_RELEASE=1`, served statically) in headless Chromium:
`fixtures/large/doc-300p.docx` opened through the file picker, the caret at the end of the first line,
77 characters typed 70 ms apart.

**Method (PerformanceObserver + rAF):** the latency is the key
event's timestamp to the end of the first rendered frame that can contain the keystroke's drawing. A
PerformanceObserver records the surface's `kiln:input-paint` mark (the composite that draws the
keystroke's frame into the page has finished); a `requestAnimationFrame` loop notes when each frame's
callback runs and posts a message from it, which runs after that frame's rendering; the first frame
whose callback ran after the mark is the one that presents the edit. The time to the mark alone
("keystroke → composite") is printed as a diagnostic. The first numbers stopped at the mark,
which left out the wait for the next frame (up to one vsync, 16.7 ms at 60 Hz) and understated the
latency.

| Date | Machine | Metric | p50 | p95 | Notes |
|---|---|---|---|---|---|---|
| 2026-10-17 | development machine, 3 runs, `--workers=1` | keystroke → composite | 12.3–13.7 ms | 22.5–26.0 ms | before this work: p50 ≈ 40 ms, p95 ≈ 60–180 ms |
| 2026-10-17 | development machine, 4 runs | keystroke → composite | 12.4–14.9 ms | 26.3–34.9 ms | a fifth run failed |
| 2026-10-17 | development machine, 4 runs, another build running (load 3–4.7) | keystroke → screen | 27.4–31.8 ms | 36.2–54.8 ms | keystroke → composite in the same runs: p50 14.4–19.0 ms, p95 24.7–38.2 ms |

Where the time goes (traced): the core's work per key is ~1 ms natively and ~3 ms in the web core
(execute ~1.5 ms, frame ~1–3 ms, after the layout and painting changes), the frame's decode
and composite ~2–4 ms on the main thread. The rest is waiting: Chrome renders a frame after the key
event and delivers the worker's answer after it, so a keystroke usually waits for one vsync before its
composite, and then for the next frame to show it.

**The budget as measured sits at the vsync floor.** A key event arrives at a random point of
the 16.7 ms frame interval, and its result can only appear at a frame boundary after the work is done,
so even with no work at all the keystroke → screen p95 at 60 Hz is about 0.95 × 16.7 ≈ 15.9 ms; any
work (the core's ~3 ms, the composite) puts the p95 above 16 ms. Painting in the worker
(`OffscreenCanvas`) removes the main-thread hop and the extra frame, which should bring the p95
to roughly one frame plus the work (~20–25 ms), but not under 16 ms; see the exception below.

## B12 — one web core per app

The web build has one WebAssembly module per app: `kiln-bridge-wasm` built with only that app's
cargo feature (`write`, `grid`, `deck`) into `apps/web/src/wasm/<app>/`. The page starts an app's
Worker, and so fetches its module, only when a document of that app is created or opened. Home
starts none. `cargo xtask wasm --release` (`wasm-opt -Os`, `gzip -9`) asserts < 4,500 KB for each
module.

| Module | Raw | Gzip | Against 4,500 KB |
|---|---|---|---|
| Single core before the split (all apps) | 14,188 KB | 5,423 KB | over by 923 KB |
| Write (Write and the scratch document) | 9,557 KB | 3,529 KB | 971 KB under |
| Grid | 10,670 KB | 3,939 KB | 561 KB under |
| Deck | 6,688 KB | 2,492 KB | 2,008 KB under |

Shared code (text layout, the Scene, charts, the PDF writer, the protocol's serde code) is in
every module, so the three together are 26,915 KB raw, but a page only loads the module of the
document it opens. The Grid module is the largest. Its room (561 KB) is what Grid can grow by before
the next step: move the protocol's command (de)serialisation to postcard, or split Grid's analysis
features into a second lazily loaded module.

Web start and open, production build (`vite build`) served with gzip, headless Chromium on this
machine, no network throttling, median of 3 fresh contexts (cache empty). Start is navigation to
`#/<app>` until the new document's first painted canvas. Open is from Home: from the moment the file
is chosen in File ▸ Open until the document's first paint.

| App | Wasm fetched before → after | Start before → after | Open before → after (file) |
|---|---|---|---|
| Write | 5,483 KB → 3,575 KB | 318 ms → 283 ms | 179 ms → 267 ms (`doc-300p.docx`) |
| Grid | 5,483 KB → 3,983 KB | 315 ms → 303 ms | 2,912 ms → 3,020 ms (`sheet-1m.xlsx`) |
| Deck | 5,483 KB → 2,517 KB | 298 ms → 282 ms | 244 ms → 330 ms (`deck-200.pptx`) |

Opening from Home's file dialog is ~90 ms slower: before the split, Home started the one core
when the dialog opened, so the core loaded while the file was being chosen. Now the core is known only
from the chosen file's extension, so it starts afterwards. A recent file, whose extension is known,
does not pay this. On a "slow 4G" link (1.6 Mbit/s) the module download alone falls from ~27 s to
~18 s (Write), ~20 s (Grid) and ~13 s (Deck). B12's time-to-interactive target (< 2.5 s on 4G) is
measured on Kiln Home, which starts no core, in "B12 — the web app on GitHub Pages" below.
